# Bank / Per-Slot Stash (Phase 4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give each character slot its own `bank` — a second container holding items AND currency, with atomic deposit/withdraw between the bank and the slot's inventory/currency. Inherits 3a/3b's stable-uid + container-owns-item + atomic-move guarantees; introduces no new dupe surface (bank items stay in exactly one slot's self-contained subtree).

**Architecture:** A new slot-scoped `bank` slice owned by a new `BankServiceServer`. Bank items are the *same* `InventoryEntry` union Inventory already validates and places — so rather than re-derive shape/placement logic, this phase **extracts two pure modules from `InventoryServiceServer`** (`ContainerValidation.checkEntryShapes` and `ContainerPlacement.planStackPlacement`) and parameterizes the one thing that differs between containers: the room-check policy (Inventory = per-kind cap; Bank = flat total cap). Deposit/withdraw are 2-op `PlayerDataService:transaction()`s, the exact container-move pattern equip/unequip uses. Currency moves the same way between `currency` and `bank.currency`.

**Tech Stack:** Roblox / strict Luau (`--!strict`), ProfileStore, Charm + charm-sync, Cmdr, TestEZ.

Spec: `docs/superpowers/specs/2026-07-17-bank-design.md` (verified against the live game 2026-07-18: old bank stored items+currency, NPC-gated at Siren's Respite, single-character-per-player so its scope can't inform per-slot-vs-account — the per-slot call is a first-principles developer decision).
Branch: `feat/bank-per-slot-stash` (rebased onto `main` after PR #8 / Phase 3c merged — so the extraction below is of the POST-affix `validateInventory`, which now also validates each unique entry's `affixes`/`statRolls` via `InventoryUtils.validateModifierMap`).

## Global Constraints

- **`--!strict` everywhere. No `any`, no casts.** A `::` cast needs genuine justification, a comment at the site, and human sign-off.
- **Spec-first TDD.** `SpecRoots.assertAllModulesSpecced` fails the build for an unspecced first-party module. Every new module gets a `.spec.luau` sibling written FIRST.
- **Plain commit messages. NO `Co-Authored-By:` / `Claude-Session:` trailers.**
- **Server-authoritative.** Clients read the synced `bank` slice; deposit/withdraw are server methods.
- **No headless test runner.** Gate = FULL `bash scripts/check.sh` (WITH `wally install`). TestEZ runs on Open Cloud on a PR into `main`. On Windows, prefix python-touching gate runs with `PYTHONUTF8=1` (the project-rules helper reads `git diff` as cp1252 otherwise).
- **No migrations** (pre-launch, data wiped) — schema changes are free.
- File-length gate: 400 code lines/module. Project-rules gate judges added lines.
- **The extraction (Task 1) must be behavior-preserving.** `InventoryServiceServer`'s public behavior and every test-observable rejection message stay byte-for-byte identical — the existing inventory spec is the proof harness. This includes the affix/statRolls modifier validation that landed in Phase 3c: `checkEntryShapes` must run `InventoryUtils.validateModifierMap` on each unique entry exactly as the current `validateInventory` does.
- **Old-code-is-evidence, not source.** The old `BankHandler`/`BankingService` (two parallel legacy impls) are NOT ported — this is a first-principles build on the 3a/3b contracts.

### Task 1: Extract `ContainerValidation` + `ContainerPlacement` (behavior-preserving refactor)

**Files:**
- Create: `ContainerValidation.luau` (+ spec), `ContainerPlacement.luau` (+ spec)
- Modify: `InventoryServiceServer.luau` (rewire `validateInventory` + `addStackable`)

**Read `InventoryServiceServer.luau`'s current `validateInventory`, `planStackPlacement`, and `addStackable` first.** This task lifts their shared internals out verbatim, then re-points the originals at them.

**`ContainerValidation.checkEntryShapes(items)`** — everything the current `validateInventory` loop does per entry, MINUS the container cap policy (the per-kind `KIND_CAPS` check stays in `validateInventory`):
```lua
export type ShapeCheckResult = { kindCounts: { [string]: number }, stackCountsByType: { [string]: number } }
function ContainerValidation.checkEntryShapes(items: { PlayerDataTypes.InventoryEntry }): (boolean, string?, ShapeCheckResult?)
```
Includes, per entry, IN THE SAME ORDER and with the SAME rejection strings the current code uses: `items` is a table; each entry a table; `itemType` registered; stack-vs-unique shape (quantity range / uid non-empty string, no cross-field); **`InventoryUtils.validateModifierMap(entry.affixes)` and `(entry.statRolls)` on unique entries** (the Phase 3c rule — keep it); `seenUids` uniqueness; accumulate `kindCounts`/`stackCountsByType`; and the per-itemType `maxStacks` check (intrinsic to the item def, not container policy — stays here). Returns `(false, reason)` on the first violation, else `(true, nil, result)`.

**`ContainerPlacement.planStackPlacement(items, itemType, count, stackMax, maxStacks, kind, hasRoom)`** — the current planner, with the kind-cap check replaced by an injected callback:
```lua
export type RoomCheck = (currentItems: { PlayerDataTypes.InventoryEntry }, kind: string, newEntriesNeeded: number) -> (boolean, string?)
```
The `maxStacks` spill check stays inside (def-intrinsic); the CONTAINER room decision (currently `ItemConstants.KIND_CAPS[kind]` math) moves to `hasRoom`.

**Rewire `InventoryServiceServer`:**
- `validateInventory` = `checkEntryShapes(inventory.items)` → on success, apply `ItemConstants.KIND_CAPS` over `result.kindCounts` (the existing per-kind loop + the existing per-itemType maxStacks loop is now partly inside `checkEntryShapes`; keep the KIND_CAPS loop here with its exact current message).
- `addStackable`'s `planStackPlacement` call passes a `hasRoom` that does the existing per-kind `KIND_CAPS` check (its exact current logic + message).

- [ ] **Step 1: Failing specs FIRST** — `ContainerValidation.spec.luau` and `ContainerPlacement.spec.luau` covering the extracted units directly (shape rejections incl. a modifier-map rejection; a `hasRoom` that returns false → placement refused; merge-then-spill happy path). These are NEW direct tests of the pure modules.
- [ ] **Step 2: Implement both modules**, lifting the logic verbatim from `InventoryServiceServer`.
- [ ] **Step 3: Rewire `InventoryServiceServer`** onto them.
- [ ] **Step 4: Re-run the FULL existing `InventoryServiceServer.spec`** — it must pass unchanged (this is the real proof the extraction preserved behavior: kind-cap breach messages, maxStacks messages, modifier-rejection messages, atomicity). Do NOT edit those tests to fit the refactor; if one fails, the extraction diverged.
- [ ] **Step 5: Gate passes** (full `bash scripts/check.sh`).
- [ ] **Step 6: Commit** — `refactor(inventory): extract ContainerValidation + ContainerPlacement (shared with bank)`

### Task 3: `BankServiceServer` — the centerpiece

**Files:**
- Create: `BankServiceServer.luau` (+ spec)
- Modify: `SliceManifest.luau`, `ClientStore.luau`

**Read `EquipmentServiceServer.luau` first** — deposit/withdraw mirror its equip/unequip 2-op transaction + `inventoryOp` composition exactly.

**Registration:** `bankSlice = SliceOwner.registerSlot("bank", { items = {}, currency = {} }, function(slot) return slot.bank end, validateBank)`. `dependencies = { "PlayerDataServiceServer", "InventoryServiceServer", "CurrencyServiceServer" }`.

**`validateBank(bank)`:**
1. `bank.items`: `ContainerValidation.checkEntryShapes` → then `#items <= BankConstants.CAPACITY` (flat total, summing `kindCounts`). Reuse the `maxStacks`-per-itemType result the shape check already computed.
2. `bank.currency`: reuse Currency's shape rule — registered `CurrencyType` keys, non-negative, `<= MAX_CURRENCY`. (Extract `CurrencyServiceServer.validateCurrency` to a shared/pure spot if it isn't already callable; if it is private, mirror its exact checks with the same messages — prefer reuse.)

**Service methods** (each a 2-op `PlayerDataService:transaction()`, all-or-nothing):
- `depositItem(userId, spec)` — `spec: { uid } | { itemType }`. Unique: remove the uid entry from `inventory` (capture via upvalue), insert into `bank.items`. Stackable: read the total held of `itemType` INSIDE the inventory op (live read), remove every matching stack, place the total into `bank.items` via `ContainerPlacement.planStackPlacement` with Bank's flat-cap `hasRoom`.
- `withdrawItem(userId, spec)` — the inverse (bank → inventory); re-enters through `InventoryServiceServer:inventoryOp` so Inventory's own per-kind validator refuses an over-cap withdrawal for free (no new code).
- `depositCurrency(userId, currencyType, amount)` / `withdrawCurrency(...)` — 2-op move between `currency` and `bank.currency` via `CurrencyServiceServer:currencyOp` + `bankOp`; refuse (roll back both) on insufficient source balance or `MAX_CURRENCY` breach on the destination.
- `bankOp(userId, fn)` — public wrapper over `bankSlice.op`, same shape as `inventoryOp`/`equipmentOp`.
- `getBank(userId) -> Bank?`.

**Guard/refusal split** mirrors Inventory/Equipment: `Guard.userId`, a "no profile loaded" bail before minting ops (bankSlice.op asserts on no active slot), specific `(ok, reason)` strings surfaced.

**Required spec cases (write FIRST):** deposit/withdraw unique (uid intact); deposit/withdraw whole-holding stackable (multiple source stacks collapse via merge-then-spill on the destination); atomicity (bank at `CAPACITY` → deposit refused, NOTHING moves on either side, deep-equal); withdraw breaching inventory's per-kind cap refused (re-entry through Inventory's validator); deposit/withdraw currency (insufficient-balance + `MAX_CURRENCY` refusals, both ops roll back); `validateBank` direct cases (bad entry shape, duplicate uid, total-cap breach, bad currency key, currency cap breach); slot isolation (two slots' banks independent). Seed via `PlayerDataService:_setProfileForTesting`, the pattern Inventory/Equipment specs use.

- [ ] **Steps: specs first → gate red → implement (registration, validateBank, the four transfer methods, bankOp, getBank) → add `bank` to `SliceManifest.DEFINITIONS` (`read = function(profile) return profile.slots[profile.slotState.active].bank end`) → add the `bank` atom + registry line to `ClientStore.luau` → gate green → commit.**
- [ ] **Commit** — `feat(bank): BankServiceServer with atomic item/currency deposit & withdraw`

## Deliberately NOT in this phase (from the spec)

Account-wide/shared bank (per-slot only); NPC/location-gated access (future presentation layer — verified the old game gated at Siren's Respite, but that's a UI/interaction gate, not this data layer); partial-quantity item transfers (whole-holding only; a quantity param can be added later with no schema change); transfer fees/cooldowns; per-kind bank caps (flat total only).
